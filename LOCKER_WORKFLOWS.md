# Locker Workflows

This document defines the operational workflows for SequoHub partner shops that manage physical wooden lockers, package pickup, Plan B missed deliveries, customer returns, and Sequo collection.

## Operating Principles

- A hub is a local shop partner acting as a relay point and package storage hub.
- Every package must be linked to a backend-generated `package_id`.
- Every physical placement must be linked to one `locker_id`.
- A package cannot be released without a valid QR scan or generated numeric code plus customer ID verification.
- Hub staff must never open sealed packages unless Support explicitly creates an audited exception.
- The app must favor guided flows over free-form actions because partner staff may not have logistics training.
- Backend state is authoritative. The mobile app may queue safe actions offline, but final validation must sync back to the backend.
- Sequo operations and approved AI automation may temporarily restrict a hub or a specific hub service. Partner
  staff cannot override these restrictions from SequoHub.

## Sequo Operations And AI Controls

Sequo may deactivate an entire hub or pause selected hub services when there is a risk, compliance, partner,
capacity, maintenance, or operational reason. This control is authoritative and must come from Sequo operations,
system policy, or approved AI automation running through audited backend permissions.

Service-level controls should support:

| Target | Effect |
| --- | --- |
| `HUB` | Disable all hub actions except read-only audit/history and support guidance. |
| `LOCKER_INTAKE` | Stop accepting new packages into lockers while allowing eligible stored-package pickup. |
| `CUSTOMER_PICKUP` | Stop package releases unless Sequo provides an explicit audited override. |
| `CUSTOMER_RETURNS` | Stop accepting customer return drop-offs. |
| `SEQUO_COLLECTION` | Stop releasing packages to collection agents until reactivated. |
| `PLAN_B_DROP_OFF` | Stop rerouted missed-delivery deposits at this hub. |

When only new locker storage is paused, SequoHub should make the grid unavailable for assignment and show a
clear Sequo decision notice. Packages already stored at the hub may still be collected by customers or riders
if pickup remains active.

The app must keep enforcing the last known restrictive state while offline until a fresh backend sync confirms
that Sequo has reactivated the hub or service.

## Physical Locker Model

The default hub setup is a 5x5 wooden box locker system with 25 numbered boxes.

| Property | Default |
| --- | --- |
| Locker grid | 5 rows x 5 columns |
| Locker IDs | `A01` to `E05` |
| Capacity rule | 1 package per locker |
| Oversized packages | Stored only in a configured overflow area with Support/Admin visibility |
| Perishable storage | Not supported for Plan B missed deliveries |
| Locker labels | Large visible label outside each wooden box |

### Locker States

| State | Meaning | Allowed actions |
| --- | --- | --- |
| `free` | Locker is empty and usable. | Assign package. |
| `reserved` | Locker is held for an intake flow in progress. | Complete intake or release reservation. |
| `occupied` | Locker contains one active package. | Pickup, Sequo collection, incident report. |
| `overdue` | Package is past the configured free storage window. | Pickup with fee, Support action, return-to-seller workflow. |
| `blocked` | Locker cannot be used because of damage, missing key, or investigation. | Admin/support unblock only. |
| `maintenance` | Locker is intentionally out of service. | Hub manager or Admin unblock only. |

## Verification Inputs

SequoHub supports two verification methods for customer and agent actions:

| Method | Usage |
| --- | --- |
| QR scan | Preferred method for pickup, return drop-off, package intake, and Sequo collection. |
| Numeric code | Fallback when QR scanning fails or the customer has no usable screen. |

The QR token must not expose personal data. It should reference a backend validation token that resolves to the relevant package, return, or collection action only after authentication.

### Numeric Codes

- Generated by the backend.
- Configurable length, with 6 digits recommended for customer pickup and return drop-off.
- Single-use.
- Short-lived where possible, with refresh through customer support or customer app.
- Hashed server-side.
- Invalidated immediately after successful handover or return validation.

### Customer ID Verification

Hub staff must verify customer identity before releasing a package.

Minimum process:

1. Compare the pickup record name with the presented ID name.
2. Confirm the customer has the valid QR or numeric pickup code.
3. Record verification result in the app.
4. Record ID type and masked reference only if required by policy.

Accepted ID types are configurable by market. Examples include national ID, passport, driver's license, school ID, work ID, or another Support-approved document.

Delegated pickup is disabled by default unless the backend package record explicitly allows it. When enabled, the delegate must present the pickup code and their own ID, and the app must record that the package was released to a delegate.

## Package Status Model

| Status | Meaning |
| --- | --- |
| `expected_at_hub` | Package is planned for this hub but not yet physically received. |
| `intake_in_progress` | Hub staff started package reception. |
| `stored_at_hub` | Package is in a locker and available for pickup or Sequo collection. |
| `pickup_ready` | Customer has been notified and can collect. |
| `overdue_storage` | Package is past the free storage window. |
| `return_to_seller_pending` | Package reached the configured uncollected limit. |
| `released_to_customer` | Customer pickup completed. |
| `released_to_sequo` | Package handed to authorized Sequo agent. |
| `incident_open` | Package is blocked by an unresolved issue. |
| `closed` | Workflow is complete and immutable except for audit notes. |

## Workflow 1: Standard Package Intake

Use this when a Sequo rider, merchant, or authorized agent brings an expected package to the hub.

1. Hub staff opens `Receive Package`.
2. Staff scans the package QR or enters `package_id`.
3. App verifies:
   - Package exists.
   - Package is assigned to this `hub_id`.
   - Package is not already stored or closed.
   - Package category is allowed for hub storage.
   - Package has no unresolved incident.
4. Staff visually checks external package condition.
5. Staff records condition:
   - `sealed_ok`
   - `damaged_outer_packaging`
   - `leaking_or_unsafe`
   - `label_unreadable`
   - `other`
6. Staff selects a free locker or scans the locker label.
7. App reserves the locker, then confirms placement.
8. Backend sets:
   - `locker_id`
   - `stored_at_hub`
   - `available_for_pickup_at`
   - `storage_clock_started_at`
9. Customer is notified with pickup instructions and code/QR.
10. Locker becomes `occupied`.

If the package is damaged, leaking, unsafe, wrong-hub, or not found, staff must create an incident instead of storing it normally.

## Workflow 2: Plan B Missed Home Delivery

Plan B applies when a home delivery attempt fails because the customer is not available.

### Eligibility

A package can be rerouted to a relay point only when all conditions are true:

- The delivery attempt was recorded by a Sequo rider or system.
- The customer was not home, unreachable, or unable to receive the package.
- The package is non-perishable.
- The package is not food, hot meal, refrigerated, frozen, pharmacy-sensitive, hazardous, or otherwise blocked by category policy.
- The nearest eligible hub has available locker capacity.
- The package can physically fit inside a locker or approved overflow area.
- The backend assigns or confirms the destination hub.

### Flow

1. Rider marks `customer_not_home`.
2. Backend checks Plan B eligibility.
3. Backend finds the nearest eligible relay point with capacity.
4. Rider receives reroute destination and package drop-off QR.
5. Hub staff scans rider drop-off QR or package QR.
6. App clearly labels the package as `Plan B missed delivery`.
7. Hub staff confirms the package is non-perishable and externally safe.
8. Staff assigns a locker.
9. Backend starts the storage clock at hub check-in and sends customer pickup instructions.
10. Customer pickup follows the normal QR/code plus ID flow.

### Blocked Plan B Cases

The app must block hub storage and require Support/Admin handling when:

- Package contains food or perishable goods.
- Package requires temperature control.
- Package is leaking, damaged, unsafe, or suspicious.
- Customer selected "return to seller only" as missed-delivery preference.
- No eligible hub has capacity.
- Package is too large for the locker and no overflow area is configured.

## Workflow 3: Customer Pickup

Use this when a customer comes to collect a package from the hub.

1. Staff opens `Customer Pickup`.
2. Customer presents QR or numeric pickup code.
3. Staff scans QR or enters code.
4. App verifies:
   - Code is valid.
   - Code is linked to a package at this hub.
   - Code has not already been used.
   - Package is not blocked by incident or return-to-seller status.
5. Staff verifies customer ID.
6. App shows locker location and any fee due.
7. Staff collects extra storage fees if required.
8. Staff opens locker and hands package to customer.
9. Staff confirms handover.
10. Backend invalidates pickup code.
11. Backend records:
    - ID verification result.
    - Fee amount collected, if any.
    - Staff user.
    - Timestamp.
12. Locker becomes `free`.
13. Package status becomes `released_to_customer`.

### Pickup Must Fail When

- QR or numeric code is invalid.
- Code is valid but package belongs to a different hub.
- Customer ID does not match and delegated pickup is not allowed.
- Package is in an open incident.
- Package is already marked for Sequo collection or return to seller.
- Storage fee is due and the customer cannot pay, unless Support creates an override.

## Workflow 4: Customer Return Drop-Off

Returns are covered in detail in [RETURNS_HANDLING.md](RETURNS_HANDLING.md).

Locker workflow summary:

1. Customer presents return QR or numeric return code.
2. Hub validates that the return is authorized and within 72 hours of delivery.
3. Hub verifies customer ID.
4. Hub records visible condition without approving the refund.
5. Hub assigns a locker.
6. Package waits for Sequo collection and final validation.

Return packages do not follow the same customer storage penalty logic because the customer has already handed the item back to Sequo's network.

## Workflow 5: Sequo Collection

Use this when a Sequo collection agent retrieves returns, uncollected packages, or packages needing support review.

1. Agent presents collection QR or `collection_batch_id`.
2. Hub staff scans QR or enters batch code.
3. App verifies:
   - Agent is authorized.
   - Batch belongs to this hub.
   - Listed packages are currently stored in this hub.
4. App shows required lockers.
5. Staff retrieves only listed packages.
6. Staff and agent confirm count.
7. App records agent identity, staff identity, timestamp, package IDs, and exceptions.
8. Lockers are freed.
9. Package statuses become `released_to_sequo`.

If a listed package is missing or damaged, staff must create an incident before completing the batch.

## Incident Handling

| Incident | Required action |
| --- | --- |
| Invalid code | Do not release. Record failed attempt and direct customer to Support. |
| ID mismatch | Do not release unless Support authorizes a documented override. |
| Wrong hub package | Reject intake or open Support incident. |
| Full lockers | Block intake and request reroute or overflow approval. |
| Damaged package | Photograph external condition if policy allows, store only with Support approval. |
| Perishable Plan B package | Reject hub storage and escalate. |
| Missing package | Lock affected locker in `blocked` state and open incident. |
| Unsafe package | Do not store. Escalate immediately. |

## Audit Requirements

Every locker event must write an audit record:

- `event_id`
- `event_type`
- `hub_id`
- `locker_id`
- `package_id` or `return_id`
- actor user ID
- actor role
- timestamp
- device ID
- previous state
- new state
- verification method
- fee amount, if any
- incident ID, if any
- sync status

## Acceptance Criteria

- Staff can see the 5x5 locker grid and current state of every locker.
- Staff can receive a package using QR scan or manual package ID fallback.
- The app blocks food and perishable packages from Plan B hub storage.
- Customer pickup requires QR/code validation and ID verification.
- Pickup code is single-use and invalid after successful handover.
- Storage fee due is shown before package release.
- Sequo collection requires an authorized manifest.
- Every locker state change is auditable.
